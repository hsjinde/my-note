## 1. my-note-web 同步事故（9/9）

線上筆記站（note.19980803.xyz）的內容來源是本 vault 的 GitHub repo，靠 webhook 增量同步。

- **發現的狀況**：284 篇公開筆記只有 112 篇正確——117 篇缺漏、55 篇內容停在 6 月、1 篇已刪未清
- **根因有兩層**：`incrementalSync` 只信任 push payload，webhook 漏送一次，那些檔案就**永久**漏掉，之後沒有任何機制補回來；而 webhook 一旦失效（設定被刪、secret 改掉）也不會有任何警訊，對帳自然一次都不會跑。所以不是壞了才發現，而是壞了三個月都安靜
- **修法：tree 對帳取代信任 payload**。`reconcileSync` 用 tree API 的完整 blob sha 清單比對，只抓有差異的、並移除 GitHub 上已不存在的——漏送的變動下一次就自動補回。幾個護欄：
  - 單次抓取上限 40 檔（Workers subrequest 限制），其餘以 pending 回報
  - tree 被截斷時直接丟錯，**避免拿半套清單誤刪整批筆記**
  - webhook 只認目標分支，其他分支的刪檔不再影響正式站
  - 新增 `POST /api/reconcile`：vault 變大後 fullSync 可能撞 CPU 上限，分批補齊這條一定會終止
- **Cron Trigger 每小時對帳**（同日）：webhook 降為快速路徑，排程當保險——webhook 正常時幾秒更新，死掉時最多落後一小時且會自己痊癒。排程先跑對帳、再用剩下的抓取預算回填日期，兩者共用上限避免單次超限
- **「最近編輯」排序原本等於沒作用**（同日）：排序與顯示用 frontmatter 的 `date`，但 284 篇只有 18 篇寫了這個欄位（94% 空白），真正的編輯時間 KV 從來沒存過。新增 `updatedAt` 並與 `date` 語意分開，由對帳（sha 變化時）與網頁編輯／新增／速記三條寫入路徑維護；fullSync 整批重寫時沿用 sha 未變筆記的 `updatedAt`，否則跑一次同步就會把全站「最近編輯」重設成今天。舊筆記的真實時間只有 commits API 拿得到（tree 與 contents API 都不帶時間），交給排程分批回填，約 9 小時補完 329 筆
- **跟八月是同一類失效**：8/1 那次是 fail2ban「三個 jail 全綠、封鎖數字在漲，卻看不見 96% 的攻擊」（見 [[2026-08 工作紀錄]] §2–3）；這次是自己寫的同步管線「webhook 在跑、站也正常開，內容卻凍結三個月」。**「有在跑」不等於「看得到」**，而且這次發生在自己的系統上。修法也同一個方向：不信任單一路徑的回報，定期拿完整清單去對帳

## 2. 大阪行程收斂（9/3–9/7）

月底出發前的最後一輪，重點從「網站功能」轉到「行程本身會不會撲空」。

- **依實際營業時間重排**（9/7，`Osaka-vault`）：查證後修掉五個會實際撲空的排程——難波八阪神社原註誤寫關門時間、黑門市場下午攤商陸續收（改定位為逛街而非正餐）、美國村與 HARBS 打烊順序對調、四天王寺中心伽藍須 15:30 前入場、回程從飯店到車站實測約 25 分，原出發時間趕不上預定班次。Day 3 改成單向推進不折返
- **時段對撞與趕不上的環節**（同日）：同一時段排兩件事的降為備選、下午路線去掉折返、補上漏排的午晚餐格；註明 Metro 一日券不涵蓋北大阪急行、Amazing Pass 結案不買、周遊券因箕面萱野不在範圍內不買。**未查證的營業時間一律標 📌，不自行填補**——這條是整輪最該留下的紀律
- **資料修正**：一筆訂位人數從筆誤的 6 位更正為 2 位（使用者確認），連帶移除當初因人數不明而寫的保守註記（「4 人以上叫 2 台」之類）
- **實體擴充**（9/7）：新增 34 筆美食、景點與購物實體並更新 Google Maps 清單
- **網站端**（`Osaka-web`）：每日行程每一列附 Google 地圖連結（9/7）——對得到 vault 實體就用實體名稱加區域搜尋，同名分店才不會搜到另一間；交通與只剩動作的住宿時段（退房、寄放行李）刻意不掛，因為沒有地點可搜。提交行程失敗時說得出原因（9/3）：原本只會看到 `Failed to fetch` 或 `502`，分不出是該重登、網路不通還是 Worker 的 GitHub token 過期，改由 Worker 分類回傳（`github-auth`／`github-missing`／`github`）、前端翻成中文並加 20 秒逾時；驗證錯誤會指出第幾天第幾個時段並直接跳過去
- **儀表板回寫實際被大量使用**：9/4–9/7 共約 20 筆 `chore(itinerary): 從儀表板更新每日行程`——7/9 做的「網站編輯 → Worker commit 回 vault」雙向管線，在真正排行程的這幾天成了主要編輯路徑
