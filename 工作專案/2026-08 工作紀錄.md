## 2. VPS 安全巡檢（8/1）

用 `server-security-audit` skill 對自架 VPS 做例行巡檢，掃 Docker、防火牆／SSH／fail2ban、mail server 三塊。10 個容器與既有記錄相符，沒有新增對外綁定；SSH 歷來成功登入全數來自已知金鑰。

- **找到並修好一個真實漏洞**：`postfix-docker` jail 的 regex 寫成 `postfix/\w+\[`，只匹配得到 25 埠的 `postfix/smtpd`。Postfix 的 submission／smtps 監聽器叫 `postfix/submission/smtpd`、`postfix/smtps/smtpd`，中間那個 `/` 不是 `\w`——**587 與 465 埠上的每一筆 SASL 認證失敗都被靜默漏掉**
- 陰險之處在於封鎖歷史看不出破綻：攻擊來源 7/22 還在打 25 埠時有被正常封鎖過，之後整批搬到 587。7/25–8/1 這週 96% 的攻擊 fail2ban 完全沒看到，兩個分散式字典攻擊網段每個 IP 每天約 7 次、早已超過 `maxretry=5` 卻一次都沒被封
- 修法與驗證：regex 改 `postfix/(?:\w+/)?\w+\[`，`fail2ban-regex` 全日誌從 13135 → 13972（+837，正好等於漏掉的 784+53，舊有的一筆沒少）；`reload` 即可不必重啟；另塞合成 log 做端到端實測確認真的在計數。同時確認 `dovecot-docker` 沒有同類問題
- 教訓：**「有在跑」不等於「看得到」**。三個 jail 狀態全綠、封鎖數字也在增加，光看儀表板永遠發現不了這個洞——要對照原始日誌的實際筆數才抓得出來

## 3. watchdesk — 把那次排查做成工具（8/18–8/21）

新專案（[hsjinde/watchdesk](https://github.com/hsjinde/watchdesk)，Python + systemd timer + SQLite，MIT）。§2 的排查是手動做完就沒了，這個把它變成每輪自動跑的檢查：**唯讀、只在規則先觸發後才叫 LLM、每個結論都要指得出證據**。定位不是儀表板——儀表板正是上次沒抓到洞的原因。

- **核心手法：三個獨立來源互相打臉**。不問 jail「你還好嗎」，而是對同一個時間窗算三個數——watchdesk 自己用比任何 filter 都寬的 matcher 數（A）、把磁碟上的 failregex 套回原始行數（B）、從 `fail2ban.log` 自己的 `Found` 事件數（C）。A>B 代表 filter 比現實窄（八月事故就是 212 對 2）；B>C 代表磁碟上的 filter 不等於記憶體裡的（`reload` 回 OK 卻沒生效，config review 永遠看不出來，因為 config 是對的）；C>0 而 A=0 則是 watchdesk 自己的 matcher 漂了——偵測器不豁免於出錯。`fail2ban-regex` 當第四方意見
- **把 C 算對花了兩次修正，兩次都先給出很有信心的錯答案**：`Found` 有兩個 logger 在發（`filter` 每行一筆、`observer` 用同樣字眼敘述自己的 ban-time 評分），全算會讓健康的 jail 多 25%；fail2ban 自己的 timestamp 是「讀到那行的時間」而不是「那行發生的時間」，只有結尾 `- <date>` 才能跟容器日誌比對
- **驗收測試餵真實事故日誌**（8/18 stage 1，`replay`）：212 筆認證失敗中 210 筆在 submission 監聽器上、jail 完全看不見，coverage 0.0094，而三個獨立計數在 6 一致——正是這個一致讓 212 這個數字可信。`tests/test_replay_gap.py` 逐條斷言上面每個數字。跨兩天重播還測到「**沒報**什麼」：真實失敗數 212 → 226 幾乎沒動，沒有任何規則謊報一場不存在的攻擊
- **stage 0 先做脫敏閘門，才准做別的**（8/18）：`redact.py` 在兩個出口強制執行（送 LLM 前、推 Discord 前），`leakcheck.py` 刻意重寫一份 pattern 而不是 import——共用會讓錯誤自己藏住自己。誠實註記寫在 README 顯眼處：攻擊者位址是**加鹽假名不是匿名**，IPv4 只有 32 bit，握有 salt 的人幾秒就能反推
- **LLM 只寫分診散文，每句話都要過機械檢查**：沒引用的丟掉、引用不存在的 ref 丟掉（捏造的引用最能騙過快讀）、講了沒人量過的數字丟掉；量過但沒在自己引的 ref 裡則降級為 hypothesis 並附理由；任何因果敘述一律標 hypothesis。端點不通或整份被駁回時，仍只用規則產出簡報並說明。規則是產品，散文是附加
- **stage 4–5：sinks、systemd unit、Alertmanager adapter**（8/18）。unit 跑 root（fail2ban socket 是 `srwx------ root root`、容器日誌目錄 root-only、`docker` group 本來就等同 root），但用 `ProtectSystem=strict` + 只留 `CAP_DAC_READ_SEARCH` 把爆炸半徑縮到最小——實測沙箱下連 `iptables -L` 都被拒。用 timer 而非 daemon：oneshot 掛了下一輪會重試並留下 journal，daemon 卡死則會安靜得跟健康系統一模一樣，而那正是這專案要對抗的失效模式。Alertmanager 走檔案 spool，**不開任何 listening socket**，且把 annotation 當不可信輸入處理（長度上限、只當證據不當指令）
- **CI 立刻抓到一個只在別人機器上會發生的 bug**：fake-stack 用兩個 busybox 容器重播真實日誌、經過真的 log driver 讀回來。runner 不是 root 所以走了 `docker logs` fallback，回傳純文字而非 json-file 格式，parser 從一個爆量的容器數出 **0** 筆失敗。修法不是硬解析，而是讓 fallback 標明自己不是 wire-format、cross-check 直接拒跑並用 `fail2ban.jail.cross_check_unavailable` 明說檢查做不了——這專案唯一存在理由的那條規則若給出有信心的假警報，比承認查不了更糟
- **Discord sink 的版面與重送抑制**（8/21）：情境未變（哪些規則、什麼嚴重度、什麼標籤——不看散文）就不重送，避免頻道被洗到靜音；規則產出的 finding 與 LLM 的 claim 排版刻意不同，格式相同等於要讀者同等信任兩者。截斷改成整塊丟棄而非砍字元（半個數字看起來像小數字），相關性事件只印一次
- **`llm.language` 可指定散文語言，數字不行**（8/21）：規則標題與 signal 名維持英文（是 grep 的錨點，翻譯過的 ref 會被 `catalogue.resolve` 拒絕）；數字釘死 ASCII，因為捏造檢查用 `\d` 比對，全形或中文數字會讓一句宣稱**繞過檢查而非被擋下**
- 現況：實機一輪 92 個 signal、0 收集錯誤、健康時 0 findings（對於一個「沉默要有意義」的工具，這是最重要的結果）；第一次開 disk source 就報出 `/` 已 97% 滿，而且 finding 自己標明「這是水位不是趨勢，要看 fill projection 才知道有沒有在動」（呼應 §9 的磁碟待辦）
